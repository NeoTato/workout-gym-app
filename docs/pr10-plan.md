# PR 10: JSON backup and atomic restore

Branch: `feat/json-backup-restore`, based on merged PR 9. Leave unmerged for phone review.

1. Define and test the first shipped backup format against the implemented native schema, rather than inventing the future entities in the original blueprint. Use camelCase DTOs, original IDs/units/snapshots, archived records, routines, goal history and the active draft. Preserve incomplete draft input. No app preferences exist yet; system appearance and per-exercise units are the current behavior.
2. Strictly validate JSON shape/version, size (50 MiB), types, unique IDs/positions, relationships, measurement modes/conventions, complete-session rules, Home, goal history and original-timezone dates. Unknown fields/versions are rejected, not silently dropped. Add adversarial/round-trip tests before exposing replacement.
3. Add schema 7 internal revision metadata and transactional triggers for every user-data table. Export a consistent snapshot on the existing serialized queue. Bind restore inspection to a SHA-256 digest and database revision. Re-read selected bytes on confirmation; reject stale inspections. Replace in one transaction, preserving the existing migration version and rolling back on any failure.
4. Add native file picker/cache/share adapters using SDK 58 APIs and a web download/file-input adapter. Picker cancellation is harmless. Sharing cancellation cannot be mistaken for a durable backup. No cloud service, upload, authentication or native project generation.
5. Add a Backup and restore page from Settings, opened with the top-right Home gear: export, inspection counts/date range/draft indication, optional current-data export, explicit replacement confirmation, busy/error/retry states and success. Reload Home queries after restore. No writes occur from picking/inspecting a file.
6. Verify real SQLite migration, round trip/file reopen, stale data/file, malformed files, injected transaction failure, component/adapters, full regressions, SDK compatibility, exports, audit and actual browser journeys. Document native device checklist and open draft PR 10.

Trust boundaries: user-selected file bytes, names and JSON are untrusted. Paths/SQL/schema identifiers only come from app code. Imported DTOs cannot supply executable SQL, filesystem paths, metadata revisions or database migration versions. Confirmation authorizes replacement of user data only. The serialized store owns the whole restore transaction; revision triggers roll back with it. A preview is never permission to overwrite.

The unshipped target v1 envelope will be refined into the first native v1 contract before this PR ships. It will not claim to support future timed/distance workouts, custom-type catalogs, notes or preferences that the app does not store. Future portability expansion requires a format migration, not ignored fields.
